  **Surface covered.** The gate iterates every workspace module that has a `go.mod` and a version tag of its own line (`Taskfile.yml`, `api:check`: `for dir in . adapter/*`): the root module against `v0.1.0`, and `adapter/otel` against `adapter/otel/v0.1.0`. `tools/apicheck` loads every non-test `.go` file of the module directory it is given, so a root-module run also reads the `examples/` tree — that is why the two `examples/*` differences above appear in the root module's report. `adapter/otel` is unchanged against its tag.

  **The resolved policy.** `docs/design/compatibility.md`, "Gate": "CI fails on an incompatible change in any module at `v1` or later and only reports for `v0` modules." `tools/apicheck` implements it — it derives the module's major version from its tag and exits 0 with the differences listed while a pre-v1 module differs, and fails from `v1` on. The run above is that behaviour: the root module is `v0`, so 13 differences are printed and the task exits 0.

  **Reading the 13.** Every one is a genuine, source-visible change made after the `v0.1.0` cut while the module is `v0.x`; the gate is doing its job, not reporting noise. Additions and fields:

  - `FlowFunc` gained variadic `FlowOption` parameters (`gohan.AllowAnonymousFlow`, `core/flow.go:42`).
  - `chains.Explanation` gained `Fallback`, `Granularity`, `Limits`, `Sample`, `Strategies` and `ToolSteps` — the widened `Explain` projection.
  - `runtime.AgentRun` gained `ModelEffect` and `BatchEffect` (the extracted native step effects, ADR-0150).
  - `runtime.Batch` gained `Scheduler`.
  - `stores.Checkpoint` gained `RunID`; `stores.Lease` and `storetest.Lease` gained `Generation` (the one-winner lease fence).

  Removals and signature moves, each matched by a replacement in the tree:

  - `runtime.ErrBatchOverrun` moved to `types.ErrBatchOverrun` (`core/types/errors.go:120`) so `core/chains` no longer depends on `core/runtime`.
  - `std.Preset.PromptMiddleware` is gone; the prompt set is declared through `gohan.WithPrompts` and the renderer is `std.PromptMiddleware` (`std/prompts.go:18`).
  - `std/flow.Classify` and `std/flow.Extract` now take the resolved `*gohan.Stack` and flow name instead of a `types.Model`.
  - `examples/excursions.Trip` and `(*LiveFlags).Snapshot` in `examples/temporal-travel` are example-local shapes that changed with the governed path and the scripted model surface.

  All are recorded under *Breaking* in `CHANGELOG.md`. One false positive was fixed before this run: `tools/apicheck` compared parameter *names*, so a pure rename was reported as a break. Parameter names are now dropped from the compared shape while arity and grouping still compare (`tools/apicheck/main.go`, `fieldList`; covered by the "parameter rename is compatible" and "method parameter rename is compatible" cases in `tools/apicheck/main_test.go`, green: `ok github.com/victorzhuk/gohan/tools/apicheck`).

**Freeze rule.** From v1, a port never gains, loses or changes a method. New capability arrives as a new optional interface discovered by type assertion; the spec that introduces it states core's behaviour when the assertion fails (`docs/design/compatibility.md`, "Ports and handles"). The pattern is already real, not aspirational — two shipped instances:

- `stores.PreemptedLister` (`core/stores/runs.go:121`): optional on `Runs`. `RecoverPreempted` asserts it (`core/recover_preempted.go:17`); when the assertion fails the recovery path degrades gracefully — the preemption tree is simply unavailable, no error — and `storetest` exercises both paths (`core/stores` tests, row 33.90 of `openspec/changes/m0-core/tasks.md`).
- `stores.MemoryStore` (`core/stores/optional.go`): optional on `NotesStore`. Session notes work on every `NotesStore`; subject memory needs `MemoryStore`, and registering the memory tool on a store without it fails with `types.ErrMemoryStoreRequired` ("gohan: subject memory needs a MemoryStore").

### Handles (implemented by gohan only; may gain methods in a minor)

`Conversation` (`core/conversation.go:19`) and `Flow[In, Out]` (`core/flow.go:15`, methods `Invoke` and `Resume`). Users do not implement handles; `testkit/gohantest` ships the fakes. A handle may grow methods in a minor release — that is a compatible change and is not gated.

### Errors

- 32 sentinel errors, one per capability spec, declared across `core/types` and `core/stores` with the spec's exact message strings; the catalog in `openspec/specs/messages/spec.md` maps each to a Problem code (`core/types/errors.go`, header comment; count from `task spec:types`: `'error': 32`). Identity is stable; messages are not (`docs/design/compatibility.md`).
- Typed errors in `core/types/errors.go`: `SuspendError` (never crosses a transport — catalog waiver), `GuardBlockedError`, `AbortError`, `LimitExceededError`, `UncertainOutcomeError`, `PartialError`, `StepError`, `ModelError` with `Retryable()`, `ErrManifestDrift`, `ErrToolCollision`, `ErrToolSetDrift`.
- Model error classes: `types.ErrorClass` with `ClassRateLimited` and `ClassTransient` among its members (`core/types/errors.go:161-164`); `ModelError.Retryable()` is true exactly for those two.

## v1-candidate declaration

**What v1-candidate promises.** The exported core vocabulary (`core/types`, 258 types per `task spec:types`), the ports and handles listed above, the sentinel/typed error set, and the optional-interface growth pattern are now shaped as they are intended to survive into `v1.0.0`. Breaking changes remain possible while the root module is `v0.x` (through M2), but each one is listed in `CHANGELOG.md` under *Breaking*, and every growth is expressed as an optional interface so the assertion pattern stays real (`docs/design/compatibility.md`). After the freeze tag, `task spec:types` fails when a port's method set changes, and `task api:check` gates incompatible changes in any module at `v1` or later.

**What v1-candidate does not promise.**

- No `v1.0.0` tag is released. The root module is tagged `v1.0.0` only when M2's exit criteria pass; core and `std` version together, adapters get their own `v1` when their conformance suites pass against core `v1` (`docs/design/compatibility.md`, "Versions and timeline").
- The method sets of illustrative-tier types (e.g. `Runtime`, `Stepper`, `Option`, `Stores` — see the Tier column in `docs/design/types.md`) may still change before the freeze; v1-candidate covers the normative tier's shape and the process, not a promise that no `v0` break remains.
- Handle growth (`Conversation`, `Flow`) in a minor release is compatible and expected.
- The three offline acceptance processes no longer cover only the store ports. They now register a flow definition with `gohan.WithNativeAgent` and construct the handle with `gohan.NewNativeConversation` — all five example packages do (`examples/{quickstart,excursions,kafka-refunds,camunda-invoice,temporal-travel}/main.go`), so the governed driver API (`Build`, the native constructor, the batch gate, the resume and recovery paths) is exercised against the memory stores. `task examples:test` is green over all five.
- What is still not exercised by the examples: `std/flow`. `Classify` and `Extract` changed signature in this window (see the gate evidence) and no example imports `std/flow` — only `std.Journal` and `std.CanonicalFingerprint` are used, both from `examples/kafka-refunds`. Their three packages (`std/flow/classify_test.go`, `extract_test.go`, `principal_test.go`) are the only coverage they have. `Explain` is likewise exercised only from `core/explain_test.go` and `std/structured`, not from an example.

**Gap against the full `compatibility.md` gate (recorded, not invented).** The gate's second clause — "`task api:check` … diffs `api/gohan.yaml` against the generated `adapter/httpapi` server; the document is versioned with the root module" — cannot be exercised yet: `api/gohan.yaml` does not exist (`ls api` → not found) and `adapter/httpapi` does not exist (only `adapter/otel` is present). Both are M4 deliverables (`docs/design/architecture.md` §5: `adapter/httpapi/` "REST + SSE transport generated from `api/gohan.yaml`"; the 2026-10-04 review note on row 1: "`api:check` with `adapter/httpapi` in M4"). The current `api:check` in `Taskfile.yml` implements only the apidiff-per-module half. This gap is recorded here rather than papered over; M4 must extend `task api:check` when `api/gohan.yaml` and `adapter/httpapi` land.

## Review verdict

The core API review gate of ADR-0083/ADR-0136 **passes on the compatibility clause too**. The resolved policy is the one `docs/design/compatibility.md` already stated: a module at `v0.x` reports incompatible changes without failing, and CI fails only from `v1` on. `tools/apicheck` implements it, and the re-run of `task api:check` against `v0.1.0` and `adapter/otel/v0.1.0` exits 0 while printing all 13 pre-v1 differences and the line `module is pre-v1, reporting incompatible change(s) without failing`; `adapter/otel` is compatible with its own tag. The differences are real source-visible changes, not noise, and each is listed under *Breaking* in `CHANGELOG.md`; the owner decision the earlier draft left open is now settled by the policy, not by a tag or a re-cut baseline. Core types and ports remain declared **v1-candidate**: no `v1.0.0` tag exists, the root module stays `v0.x` until M2's exit criteria pass, and the M4 gate artifacts (`api/gohan.yaml`, `adapter/httpapi`) are still missing — recorded above as open work, not a silent omission.
