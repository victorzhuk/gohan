# ADR-0092: MCP 2026-07-28 binding and `AwaitingInput`

Status: accepted · Origin: grill round 18 (2026-09-29)

## Decision

Core gains one suspension reason, `AwaitingInput{Prompt, Schema}`, with schema-validated `Deliver`. `adapter/mcp` binds to the 2026-07-28 protocol: client maps `input_required` to `HumanApproval` (confirmations) or `AwaitingInput` (data) and replays `tools/call` with `inputResponses` under the same `CallKey`; Tasks become `AwaitingTool` woken by `subscriptions/listen` or a `Waker` poll; catalog `ttlMs` drives manifest refresh with the existing fail-closed drift check; annotations may only lower effect. Server maps `HumanApproval`/`AwaitingInput` to `input_required` with the token in `_meta`, the stateless retry to `Resume(token, in)` with the OAuth principal as approver, and long flows to the Tasks extension. No MCP host surface in core.

## Context and evidence

The earlier §7.7 design returned suspensions as MCP errors because the protocol had no lifecycle; MRTR and the Tasks extension now map one-to-one onto `SuspendError`/`Resume` and `AwaitingTool`/`Waker`. Structured elicitation had no reason in core and is a native need too (choosing among options mid-run). Permission remains the host's: approval still enters only through `Resume` with a transport-set approver.

See `docs/design/evidence.md` for the published sources behind this decision.

## Consequences

New capability `interop`; `suspension` gains `AwaitingInput`; `docs/design/adapters.md` §7.7 rewritten. Supersedes the MCP paragraph of ADR-0074.
