# Design: m2-research-report-example

## Context

See `proposal.md` — Why. This design fixes the seams the example composes and maps every accepted scenario id to its owner, its subtest and its evidence. Read against the tree on 2026-10-12:

- **The composition pattern already exists.** `examples/excursions/main.go:29-85` builds a stack with `gohan.Build(append(std.Defaults(), WithStores, WithModels, WithNativeAgent)...)`, registers a `gohan.NativeSpec`, obtains `gohan.NewNativeConversation` with `WithConversationRuns` and `WithConversationEventLog`, ranges `conv.Send`, then loads the history through `stores.MemorySessionLog.Load` and reports the persisted messages. The example copies that shape; it persists nothing by hand.
- **The context policy is a per-flow field, not a global.** `stores.ContextPolicy{Projections []Projection, Compactor Compactor}` (`core/stores/projection.go:30-33`) rides `NativeSpec.ContextPolicy` (`core/native_options.go:40-43`), and `gohan.WithContextPolicy` (`core/build_options.go:300-306`) binds it across every registered native flow. `Stack.ContextPolicy(name)` (`core/native_options.go:60-65`) reads it back, so the README can state the resolved policy from the same path the harness uses.
- **Projections run before the caller assembler and never write.** `withProjections` (`core/native_effects.go:424-443`) clones the loaded history, applies each projection over the copy, and hands the copy to the assembler. `collapseBeforeProjections` (`core/native_effects.go:31`) puts the compaction collapse ahead of it, so the example gets the compaction view and the projections in the declared order without editing the pipeline.
- **Compaction is durable through the same append path.** `runCompactionStage` (`core/compaction_stage.go:298`) binds the store's compaction append into the existing `HistoryAppender` execution path (`core/drive_lifecycle.go:104`, `:160-165`); the publication is durable before the append completes. `std/context.Summarize` is a `stores.Compactor` (`std/context/summarize.go`).
- **Deferred discovery ships and filters per turn.** `types.ToolSpec.Deferred` (`core/types/tool.go:89`); `std/toolsearch.NewSearchTools(registry)` builds the reserved `search_tools` meta-tool (`std/toolsearch/search.go:31`), `DeferredFilter(active)` (`std/toolsearch/activation.go:65`) drops undiscovered deferred tools from the assembled set, and `Save`/`Load` carry the activation set in the checkpoint (`std/toolsearch/activation.go:39-64`). The example supplies the registry closure; it does not reimplement the filter.
- **Detached lifetime needs an event log.** `core.Detached()` is a `ConversationOption` (`core/stream_lifetime.go:23-27`) that switches runs to detached lifetime; the conversation constructor refuses a detached flow without an event log (`errDetachedNoLog`, `core/stream_lifetime.go:19-21`, declared at `core/stream_lifetime.go:21`, enforced at `core/native_conversation.go:123`, `core/conversation.go:249`). `Conversation.Attach(ctx, runID, afterSeq)` (`core/conversation.go:30`, implemented at `core/attach.go:14`, specified at `openspec/specs/streams/spec.md:124`) replays persisted events in order and then live ones, gapless, as long as the cursor is still retained.
- **Notes are a session-scoped slot, not a message.** `notes_write`/`notes_read` are a `ReadOnly` tool pair with a `SlotSession` provider injecting the current notes into every request, capped at e.g. 2 KiB (`openspec/specs/working-state/spec.md:65`). `ClearToolResults` excludes `notes_read`/`notes_write` results regardless of caller configuration (`openspec/specs/context/spec.md:77`). `std/notes` ships the store and the reset behaviour (`std/notes/*.go`).
- **The recipe lanes are not in M2.** `docs/overview.md:116` assigns `std/flow` recipes — `Extract`, `Classify`, `Route`, `MapReduce`, `Pipeline`, `RAG`, `Judge`/`Refine` — to M4; `std/flow` ships `Extract`, `Classify`, `Title` and the quarantine helper only. `docs/design/scenarios.md:186` lists `MapReduce`, `RAG` and `Judge` as this example's recipes. `subflows.collect-partials` is registry-marked `deferred_to: "M3"` (`openspec/scenarios.json:1104-1109`; requirement at `openspec/specs/subflows/spec.md:133`).
- **Durable sandbox enumeration is unchanged by this example.** `types.SandboxResources` (`core/types/sandbox.go:96-99`) with `Enumerate` and `CloseByRef` is the standing enumeration contract (`openspec/changes/m2/design.md` §4.1). The research example declares no sandbox at all — its sources are read-only retrieval fixtures — so no `Sandbox` or `Workspace` method is touched and no `types.SandboxResources` assertion is introduced.

## Goals / Non-Goals

**Goals:** land one offline example that exercises deferred discovery over exactly 40 sources, guards over retrieved content, notes retention across compaction, numeric tree budgets, detached execution and client reattachment through the shipped public paths; give that composition one scenario id of its own; and document the recipe lanes the example depends on without reimplementing them. The scope of the change covers this package's own documents — `proposal.md`, `tasks.md`, `design.md` and `specs/context/spec.md` — alongside `examples/research-report`, `Taskfile.yml`, `openspec/scenarios.json`, the lane row in `openspec/changes/m2/design.md` and the M2 exit row in `docs/overview.md`; the mirrored copy under `openspec/drafts/m2/changes/m2-research-report-example/` carries the same four documents.

**Non-Goals:** no core, std or adapter code change; no new port, option, seam or store; no change to any existing scenario requirement block or to an existing id's owner; no network, credential, daemon or container in any fixture or test; no `std/flow` recipe implementation (M4); no `MapReduce`, `RAG` or `Judge` claim while those recipes are absent; no `subflows.collect-partials` claim while the registry defers it to M3; no work on `examples/data-analyst` (its own package, `m2-data-analyst-example`); no redaction or guard policy change — the example consumes the shipped guard stages.

## Decisions

### D1 — The example is a new package in the `examples` module, composed exactly like `excursions`

`examples/research-report/main.go` is `package main` in `module github.com/victorzhuk/gohan/examples` (`examples/go.mod:1`). It follows `examples/excursions/main.go:29-85` line for line in shape: `gohan.Build` with `std.Defaults()`, memory stores, a scripted `types.Model`, one `gohan.NativeSpec` (`Request: gohan.FlowRequest{Name: "research_report"}`), `gohan.NewNativeConversation` with `WithConversationRuns`/`WithConversationEventLog`, one `conv.Send`, then a `sessions.Load` to report the persisted history. Adding a module dependency is not needed: `core`, `core/types`, `core/stores`, `std`, `std/context`, `std/notes` and `std/toolsearch` are all in the examples module's existing require list. Alternative rejected: a new top-level module — the catalog rule says each example is a runnable service under `examples/`, and `Taskfile.yml` `examples:run` iterates `./<dir>` inside the module.

### D2 — Exactly 40 deferred source tools, and the filter is the shipped one

The fixture registers 40 `types.ToolSpec` entries with `Deferred: true` (`core/types/tool.go:89`) plus the always-loaded fixtures, and passes the registry closure to `std/toolsearch.NewSearchTools` (`std/toolsearch/search.go:31`). `DeferredFilter(active)` (`std/toolsearch/activation.go:65`) then decides what each assembled request carries. Forty is the number the spec scenario states (`openspec/specs/tools/spec.md:355-357`: 40 deferred + 4 always-loaded → 5 definitions including `search_tools`) and the number `docs/design/scenarios.md:186` gives the example. The example asserts the first request's definition count and calls `Explain` for the token cost; it does not reimplement counting or filtering.

### D3 — Activation, compaction and notes are one composed run, not three examples

The run's shape: the flow calls `search_tools`, discovers a subset of sources, reads each discovered source (a retrieval fan-out), writes a progress note before the fan-out, compacts when the assembled request crosses the budget, and finishes the report. Because the activation set rides the checkpoint (`std/toolsearch/activation.go:39-64`) and the compaction publication is durable before the append completes, a run that suspends between the fan-out and the report resumes with the same active sources over a compacted history. Because notes arrive through a `SlotSession` provider rather than through history (`openspec/specs/working-state/spec.md:65`) and `ClearToolResults` never clears `notes_*` results (`openspec/specs/context/spec.md:77`), the note written before the compaction is still in the next request after it. One run proves all three together; three separate runs would prove none of the interaction that matters. This is exactly what `context.research-report-compaction` asserts.

### D4 — The numeric tree budget is spent per child and accumulated into the parent

The fan-out spends each child's cost through the normal limits path, and the parent's accumulated total is what `limits.cost-accumulates` binds (`openspec/specs/streams/spec.md` sibling id owned by `core/chains/limits_test.go:88`). The example declares a run ceiling that a wider fan-out would cross, so the composition shows the refusal rather than only the accumulation. The example passes the ceiling through the shipped `RunLimits` surface; it computes nothing of its own and adds no accounting path.

### D5 — Detached execution with an event log, reattach from the last `Seq`

The conversation is built with `gohan.Detached()` (`core/stream_lifetime.go:23-27`) and an `EventLog`; `Build`/the constructor refuses a detached flow without one (`errDetachedNoLog`), which is the `streams.detached-requires-log` contract. `Send` returns once the run is started, and the client consumes through `Attach(ctx, runID, afterSeq)`. The example's offline test consumes part of the stream, drops the connection at a known `Seq`, reattaches from it and asserts gapless, duplicate-free delivery. The example consumes `Attach` as published (`openspec/specs/streams/spec.md:124-127`); it does not reimplement retention or cursor refusal.

### D6 — One new composition id; every other id keeps its name and owner

The example adds exactly one id, `context.research-report-compaction`, under the `context` capability, because that is the capability whose requirement the composition newly makes observable. Existing ids are *reused*, never renamed or reassigned. The registry entry carries the owning ADR for the composed context behaviour (`ADR-0090`, `docs/adr/0090-context-management.md`) because the composition is a context-management guarantee; the per-capability rows it exercises keep their own origins.

Alternative rejected: one new id per composed capability (`tools.research-report-*`, `streams.research-report-*`). The example adds no behaviour to those capabilities, and a per-capability id would imply an owning change per capability for what is one example. The table below is the mapping; each row's subtest is the existing upstream proof, and the example's own test cites it rather than duplicating it.

### D7 — Recipe lanes are named as prerequisites, and the example never claims them

The catalog row lists `MapReduce`, `RAG` and `Judge` (`docs/design/scenarios.md:186`); `docs/overview.md:116` assigns them to M4 and `std/flow` does not ship them. The example therefore composes the M2-reachable path — deferred discovery, a bounded per-source fan-out, ordered collection of per-source results — and records `MapReduce`, `RAG`, `Judge` and `subflows.collect-partials` as unmet recipe prerequisites in the README and in `tasks.md`, never as evidence. The fan-out the example does run uses the shipped subflow surfaces that exist (`openspec/specs/subflows/spec.md`); the moment the M4 recipes land, task 4.1 upgrades the fan-out and its README row, with no change to any id in D6. Alternative rejected: shipping a local `MapReduce` inside the example — that would put an M4 recipe's semantics in an M2 example and freeze a second convention.

### D8 — Fixtures are deterministic and offline-only

The scripted `types.Model` answers from a fixed table keyed on the assembled request; stores are the in-memory set (`stores.NewMemorySessionLog`, `NewMemoryRuns`, `NewMemoryEventLog`, `NewMemoryJournal`, `NewMemoryAuditLog`); the 40 source fixtures are literal byte slices. No HTTP client, no credential, no daemon, no container, no clock-dependent value, no random seed without a fixed value. `std/sandbox` is not used at all: the sources are read-only retrievals, so the `PerSession` deny-all egress posture and the `SecretResolver` path in `openspec/specs/sandbox/spec.md:106-195` do not apply here, and the data-analyst sibling is where that posture is exercised. The example therefore adds no secret to any history, journal or span.

### D9 — Documentation surface: requirements → scenario ids, offline commands, public paths, fixtures, versions, explain

`examples/research-report/README.md` follows `examples/excursions/README.md` (run command, test command, offline statement) and adds the catalog rule's required content: a requirements → scenario id table (the D6 rows plus the new id), the two offline commands, the public paths the example calls, the fixture inventory, the versions it pins (the gohan module version and, for a live run, the provider model id the fixtures stand in for) and the `explain` surface. The example wires `std.ExplainHandler`'s contract as its own `explain` subcommand (JSON when stdout is not a TTY), the way `openspec/specs/chains/spec.md:163` allows, so the resolved flow, profile, steps and tool steps, the registered tools with their egress, the strategies, the fallback, the limits, the granularity, the assembled sample request, the prompts, the skills, the release and the warnings are inspectable without a debug port. The example emits exactly the fields `std.ExplainHandler` serves from `Stack.Explain` (`std/explain_handler.go:40-60`); `chains.Explanation` carries no guard and no persistence-write projection (`core/chains/explain.go:44-63`), and D1/D4 forbid the example computing any of its own, so the `explain` contract names only that surface. `Taskfile.yml`'s `examples:run` loop gains `research-report` so CI runs the entry like every other shipped example.

## Risks / Trade-offs

- [An example that reimplements harness behaviour hides composition defects] → D1 and D2 fix the example to `Build` + `NativeSpec` + `Send` + `Load` and to the shipped `toolsearch` filter; the example contains no projection, compaction, filtering or accounting logic, so a defect it hides would have to be in its composition, which is the point.
- [Forty fixtures is a lot of literal noise] → they are generated from one deterministic table by a loop in `fixtures.go`, not hand-written forty times; the count is asserted, so the fixture cannot silently shrink.
- [The detached reattach assertion can pass vacuously] → the test consumes a prefix, records the exact `Seq` it stopped at, reattaches from it and asserts both gaplessness (consecutive `Seq`) and that at least one event arrived after the cursor; a run that produced nothing after the cursor fails.
- [Composed examples rot when upstream lanes move] → every README requirement row cites the owning subtest by name, so an upstream rename or removal shows up as a failing citation rather than as a stale claim.
- [The unmet recipe prerequisites could read as done work] → D7 and the README record `MapReduce`, `RAG`, `Judge` and `subflows.collect-partials` as unmet with their owning milestones; no task checkbox turns green on them until the recipes ship.
- [A new id could be read as a new `context` behaviour] → the requirement text names the example as its subject and D6 states that no existing requirement block changed; the registry entry carries no `deferred_to` because the composed guarantee is M2-owned and this package implements it.

## Migration Plan

Additive and reversible: `examples/research-report` is a new directory in an existing module, `openspec/scenarios.json` gains one entry, and `Taskfile.yml`'s `examples:run` loop gains one directory name. No stored shape, no migration, no port, no exported symbol. Rollback is deleting the directory and reverting those two lines. Nothing in `core`, `std` or `adapter/*` depends on the example.

## Open Questions

None that change the specs, the approach, or the task breakdown. The recipe prerequisites are recorded as unmet work owned by M4 and M3 lanes, not as open questions in this change.
